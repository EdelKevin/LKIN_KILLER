# Master Prompt — Per-JD Resume Tailoring (template, v3)

You are tailoring a candidate's resume for **one** job description. Produce the final tailored resume in **markdown**, in **English**. Do not pause mid-run to ask the operator to confirm experience — the candidate reviews every output before use and owns interview readiness for every claim.

> **Note**: This is a template. The hard-fact specifics (company names, job titles, dates, locations) come from `profile/style_profile.md`, which is generated by running Phase 0 on the operator's actual resume. See `phase_0.md`.

---

## Inputs (provided by orchestrator)

All four Phase 0 artifacts live under `profile/` at the project root.

- `profile/base_resume.md` — source of truth, never overwrite (generated by Phase 0)
- `profile/style_profile.md` — voice + structure fingerprint + LOCKED hard facts (generated by Phase 0)
- `profile/skill_inventory.md` — tech ammunition + business problems + landing pads (generated by Phase 0)
- **`profile/bullet_bank.md`** — pre-written tech bullet variants. **ALWAYS check this BEFORE generating new bullets.**
- **`resume_checklist.md`** — operator-authoritative checklist (at project root). Overrides any conflicting prior rule.
- The JD URL (LinkedIn / Greenhouse / Lever / Ashby / company careers page) or pasted JD text

## Locked facts (NEVER modify)

The exact values are in `profile/style_profile.md`'s "Hard facts (LOCKED)" section. In general:

- Identity fields use `[REDACTED]` placeholders for name / email / phone / schools / company names where the operator chose to anonymize. Keep as-is.
- Each role's `company / title / dates / location` is locked — except the resume HEADER city, which may swap per JD (see step 5).
- Project titles are locked.
- Education entries (school, degree, dates) are locked.
- **Bullet counts per section are HARD-LOCKED — NEVER expand a role from N to N+1 bullets, even to fit a P0 tech.** If a P0 tech cannot land in the existing bullet count, drop a lower-priority tech from the same role's bullets instead. The locked counts live in `profile/style_profile.md` Structure fingerprint.

## Pipeline (run in order)

### 1. Fetch JD
- LinkedIn URL → extract `currentJobId` or `jobId` → hit `https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/{jobId}` via WebFetch
- Greenhouse / Lever / Ashby → public JSON API
- Workday / generic company careers page → WebFetch the page, extract from HTML
- Pasted text → use directly
- Extract: company, role_title, location, must_haves, nice_to_haves, full JD body

### 2. Extract keywords
- Scan whole JD text
- Keep only **grep-able tech**: languages, frameworks, libraries, tools, algorithms, cloud services, databases, protocols, platform SDKs
- Drop: adjectives ("strong", "passionate"), soft skills ("team player", "communication", "ownership"), generic nouns ("systems", "scale", "architecture" without specific tech), years-of-experience requirements, degree requirements
- Heuristic: "could I `grep` this in a GitHub repo's `import` / `package.json` / `Dockerfile` / `requirements.txt`?" — yes → keep; no → drop

### 3. Prioritize keywords (P0 / P1 / P2)

| Tier | Signal |
|---|---|
| **P0** | In job title, OR in "Required" / "Must have" section, OR ≥3 mentions in JD, OR is a headline stack tech ("a Java Spring Boot role") |
| **P1** | In "Preferred" / "Nice to have", OR 1–2 mentions but stack-core |
| **P2** | One off-hand mention, not stack-core (e.g. "familiar with Grafana a plus") |

### 4. Polyglot OR-list detection
- If JD lists 4+ languages joined by "or"/"/" (e.g. "JS or TS or Python or Go or Java"):
  - Check overlap with the operator's base languages (see `profile/skill_inventory.md`) → if any match, those count as hit; **don't inject more**
  - If no overlap, pick top 1 by preference (TS > Go > Java > Swift > C++) → inject into **Projects**, not Experience
- If JD says "primarily X" / "expert in X" / X is in title → X is P0, regular injection rules apply

### 5. Location swap — HEADER ONLY

Swap ONLY the top-of-resume header city. **NEVER change past-job locations** — any role's location in the Experience section is a hard fact; changing it = fabrication. The header city signals "where the candidate is now / will be" for recruiter regional filtering; that's the only legitimate location swap.

| JD location | Header location |
|---|---|
| Specific city e.g. "Seattle, WA" | use that |
| "Bay Area" / "SF Bay" | `San Francisco, CA` |
| Multiple cities "NYC or SF" | first listed |
| "Remote (US)" / empty | keep operator's base header city |
| Non-US (Toronto, London) | keep operator's base header city |

### 6. Tailor — bank lookup FIRST, then strategies

**For every JD-mentioned tech, look it up in `profile/bullet_bank.md` first:**
- Tech found in index → apply the named variant to the listed slot. NO AI generation needed.
- Tech NOT in bank → run Strategies A/B/C below, then ADD the new variant + index entry to `profile/bullet_bank.md` before exit (so future runs skip generation).

**Strategies (in order of preference)**:
- **Strategy A — Swap**: JD wants tech X; base already mentions equivalent Y for the same task → swap Y → X in the existing bullet (logic unchanged). Example: JD wants TensorFlow, base says PyTorch in CV model bullet → swap.
- **Strategy B — Embed**: JD wants tech X; base has related business context but no explicit X → embed X into that bullet. Example: JD wants Grafana, deploy bullet already has K8s on ECS → add "with **Grafana** dashboards for SLO monitoring".
- **Strategy C — Augment**: JD wants tech X; base has no related context → augment closest bullet OR add to Skills as last resort.
  - Constraints: same role / time / scale-consistent (3year/Entry/New Grad/Intern level — see §13a ceilings); coherent with surrounding bullets.
  - Strategy C is a supported last resort. The candidate commits to being interview-ready on every tech the resume claims.

### 7. Mandatory placement rules

- **P0 tech MUST land in ≥1 bullet** (Experience or Projects). Skills-only coverage of P0 = FAIL.
  - Primary injection target: **first work experience** (most recent role at the top of Experience). Walk down to older roles / Projects only if semantically incompatible.
- **P1 tech MUST appear ≥1 time** in the resume, and should land in a bullet (Experience or Projects) by default. Skills-only delivery of a P1 is allowed ONLY when the tech cannot be reasonably and naturally embedded into any bullet (no semantically compatible slot via Strategies A/B/C without breaking business-context coherence or the ≤3-techs-per-bullet cap).
- **P2 tech**: Skills is enough.

### 7a. Dedup rule

**Each tech name appears AT MOST ONCE in the entire resume.**
- If a tech is in a bullet → it must NOT also be in Skills (Skills is the *residue*, not duplicate coverage).
- If injecting a new tech into a bullet, REMOVE it from Skills (or the other bullet) if it was already there.
- Vary surface forms across bullets where possible (e.g., one bullet says `**Python**`, another says `**Django**` without restating Python — Django implies Python).
- Pre-existing base-resume repetition is acceptable as legacy but should not be amplified. Never ADD new duplication.

### 7b. ≤3 techs per bullet

A bullet may name **at most 3 NEW or distinct tech tokens** in addition to its base content.
- Counting: every `**bold tech**` token = 1. Numbers don't count.
- If injecting >3 new techs into one slot → push the lower-priority overflow to Skills (or drop). **NEVER expand role bullet count** — see §"Locked facts" + `profile/style_profile.md` Structure fingerprint.
- Bullets with 5+ tech tokens read as a keyword dump and look fake. Don't do it.

### 8. Bullet-length management
- Target 250–340 chars per bullet
- If injection pushes a bullet >360 chars: trim secondary detail (filler phrases) — NEVER trim numbers, core feature, or impact

### 9. Bold formatting
- Bold ONLY tech names and numbers in bullets: `**PostgreSQL**`, `**Redis**`, `**90%+**`, `**∼60%**`, `**<2s**`
- Do NOT bold: verbs, generic nouns, role names, company names, descriptive adjectives
- In Skills section, label is bold (`**Languages:**`), entries are plain

### 10. Verb rules (from `resume_checklist.md`, 3year/Entry/New Grad/Intern level)

**WHITELIST** (prefer these — 3year/Entry/New Grad/Intern voice):
`developed, implemented, built, created, optimized, enhanced, integrated, deployed`

**SENIOR BLACKLIST** (NEVER use — sounds inflated even for 3-year SWE):
`architected`

**CONDITIONAL** (constrained use only):
- `led` — OK only with a specific narrow object (`led migration of X`, `led 2-person spike`); BANNED with team size ≥5 (`led team of 8` ❌)
- `designed` — OK at feature / API / data-model scope; NOT for system architecture or platform-level claims

**WEAK BLACKLIST** (never use — signals low confidence):
`worked with, learnt, studied, assisted, helped, experienced, familiar with, knowledge of`

When swapping a blacklisted/weak verb, pick the closest whitelist equivalent:
- `architected` → `built` / `developed`
- `led team of N` (N≥5) → `coordinated` / `drove`, OR drop the head-count claim
- `designed <system / platform>` → narrow to `built <feature / API>` or `developed`
- `worked with` / `helped` → `built` / `developed`
- `familiar with` / `knowledge of` → drop and rewrite with an action verb

### 11. Article + grammar rules

- **Delete articles** (`the`, `an`, `a`) where possible: "Built RESTful API with..." NOT "Built a RESTful API with..."
- **Past tense** throughout; never mix tenses
- **No `<phrase>: <details>` colon-format** (signals ChatGPT-generated output)
- **No "Tech stack used: ..." footer line** under each job (looks messy, useless)
- **No company-intro line** — bake company business into bullet 1 of that role

### 12. Section title case

Use **title case**, NOT uppercase: `Education` NOT `EDUCATION`. Builders enforce this; if you ever write markdown headers manually, use title case.

### 13. Quantification realism caps (unified across 3year/Entry/New Grad/Intern)

- **Single ceiling: ≤40% improvement**, AND any claim >25% MUST name the mechanism in the same bullet (e.g., `−35% p95 latency via **Redis** cache`, `+38% retention via **A/B** test on onboarding`)
- Bare numbers without a named mechanism: cap at 25%
- BANNED: `10x` / `100x` / `1000x` without a cited source — reads as fabricated
- Numbers must be coherent across the resume (no contradiction for the same product)

### 13a. Scale realism ceilings (unified)

Upper bounds, not targets. Use whichever is true; if unclaimed in base, do not invent.

| Dimension | Ceiling | Hard ban |
|---|---|---|
| QPS / throughput | sustained ≤10K QPS, peak ≤100K QPS | ≥1M QPS |
| Data volume | ≤10TB or tens-of-millions of records | PB-scale, billions-of-records |
| User reach | ≤1M MAU / ≤100K DAU touching the feature | nine-figure user counts |
| Team scope | "led 2–3 person workstream" OK; otherwise omit head-count | `led team of N` (N≥5) |
| Tenure | NEVER write `N years of experience` — Experience header dates carry that | any `N years of …` phrasing |

Genuine outliers (e.g. a real FAANG infra role with ≥1M QPS) must be flagged in `profile/style_profile.md`'s "scale exemptions" section during Phase 0 before Phase 1 may exceed these ceilings.

### 14. Backend SWE ATS must-haves (verify all present)

For backend / fullstack JDs, ensure base bullets cover:
- ✅ RESTful API (with named language + framework)
- ✅ Database (relational + NoSQL ideally)
- ✅ Cloud (AWS/GCP/Azure with specific service)
- ✅ AI/ML (or LLM ops)
- ✅ Agile workflow
- ✅ Unit test coverage ≥90%
- ✅ CI/CD
- ✅ Docker
- ✅ Kubernetes

**Bonus**: Kafka, Cache (Redis).

## Output

Write final markdown to:
```
./outputs/{M.D}/{company_role_slug}/{company_role_slug}.md
```

- `{M.D}`: month and day with NO leading zero (e.g. `5.18`, `12.3`)
- `{company_role_slug}`: `{company_lowercase_underscore}_{role_slug}`
  - `{company_lowercase_underscore}`: lowercase, special chars → `_` (e.g. `Booking.com` → `booking_com`)
  - `{role_slug}`: lowercase title, `_` separators (e.g. `software_engineer_new_grad`)

Then run conversion (both rendered files land in the SAME folder as the .md):
```bash
python3 build_pdf.py <path-to-md>
python3 build_docx.py <path-to-md>
```

## Self-review

After the writer's draft, the orchestrator spawns a fresh-context Reviewer subagent that runs this 17-item rubric:

```
RUBRIC (17 items):
1.  P0 coverage: every P0 tech appears in ≥1 bullet (Experience or Projects, NOT Skills-only)?
2.  P1 coverage: every P1 tech appears ≥1 time, in a bullet unless no natural embed exists (Skills-only P1 must be justifiable as "no semantically compatible bullet slot")?
3.  Bullet pattern: each bullet follows `<Verb> <bold tech> <feature/business> <bold quantified impact>`?
4.  Metric density: each bullet has ≥1 number (pre-existing base gaps don't count as regressions)?
5.  Realistic scale per §13a ceilings (≤10K QPS sustained, ≤10TB, ≤1M MAU, no `led team of ≥5`, no `N years of experience` phrasing)?
6.  Single page (PDF page count == 1)? **HARD FAIL if not** — output is not shippable until this passes.
7.  Hard facts intact: companies, titles, dates, placeholders preserved; past-job locations unchanged?
8.  Bold rule: only tech names and numbers wrapped in **...**, nothing else bolded?
9.  Business-tech consistency: every injected tech fits the business context of its bullet.
10. Number coherence: no contradictory numbers across the resume for the same product.
11. ≤3 techs per bullet: split if more.
12. No duplicate tech: each tech name appears at most once across the whole resume.
13. Verb compliance: no `architected`; `led` only with a narrow object (no team-size ≥5); `designed` only at feature/API scope (not system/platform); no weak verbs (worked with/familiar with/etc).
14. Article cleanup: no unnecessary `the`/`a`/`an` in bullets.
15. Section title case: Title Case (`Education`), NOT all caps.
16. Quantification cap: ≤40% improvement; any claim >25% names the mechanism in the same bullet; no naked `10x`/`100x`.
17. No ChatGPT footprints: no `phrase: detail` colon-format, no "Tech stack used:" footer, no company-intro line.
```

Reviewer returns: `{pass: bool, rubric_scores: {1-17}, suggested_fixes: [...]}`. Reviewer does NOT rewrite — only diagnoses.

If `pass: false`: revise based on `fail_reasons` → orchestrator spawns a SECOND reviewer (still fresh context). Max 2 review rounds total. If 2nd review also fails → save md with `WARN_` prefix on filename and report to operator.

## Failure handling table

| Failure | Action |
|---------|--------|
| LinkedIn fetch returns 429 (rate limit) | Pause 60s, retry once. Still fails → mark JD as failed, continue rest, ask operator to paste JD text. |
| LinkedIn fetch returns 403 / login wall | Mark JD as failed, ask operator to paste JD text. NEVER attempt logged-in scraping. |
| Greenhouse / Lever / Ashby JSON 404 | Try the WebFetch on the human-readable URL. Still fails → mark as failed. |
| Workday URL hangs / paywall | WebFetch the page once with a short prompt. If junk → mark as failed, ask for paste. |
| Generic company careers page returns nothing | WebFetch + extract. If JD body < 200 chars → likely JS-rendered → mark as failed, ask for paste. |
| PDF page count > 1 after build | **HARD FAIL** — single page is strict. Trim secondary detail in 1–2 longest bullets (NEVER trim numbers/core feature/impact). Re-render. Still > 1 → trim more aggressively (drop filler clauses, tighten Skills lines). Never expand bullet counts. The output is NOT shippable until PDF == 1 page. |
| Reviewer round 1 fails | Revise per `suggested_fixes` → re-render → spawn fresh Reviewer round 2. |
| Reviewer round 2 fails | Save md with `WARN_` filename prefix. Render PDF + DOCX anyway. Report to operator with the fail reason. |
| Reviewer subagent can't be spawned (harness limitation) | Writer self-applies the rubric inline as a fallback. Flag in the warnings field. |
| python-docx fails | Skip DOCX silently, ship MD + PDF only, note in warnings. |
| Chrome PDF render fails | Print Chrome stderr, mark JD as fail. Operator can rerun manually with `python3 build_pdf.py <path.md>`. |
| Memory pointer file missing | Read the workdir `README.md` directly; suggest operator add the memory pointer back if missing. |
| Hard fact mismatch detected by reviewer (e.g. past-job location changed) | Auto-revert before saving (don't waste a review round on operator-fixable mistakes). |
